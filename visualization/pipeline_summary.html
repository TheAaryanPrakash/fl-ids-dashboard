FL-IDS Pipeline Summary

A federated-learning intrusion detection system, trained non-IID across simulated clients, stress-tested under label-flipping poisoning, and finally run over a real emulated network through a custom OpenFlow controller. Every number and chart on this page is read live from this project's own data and result files — nothing here is hardcoded.

1Pipeline Overview

The project runs in five stages, each building on the last. The end goal (not built yet — see the note at the end of this section) is to eventually run this whole system on top of the emulated network and have the controller act on what the IDS detects. Right now, stages 1–5 below are complete and are what the rest of this page reports on.

What each stage actually does

① Two unrelated IDS datasets

Two pre-cleaned CSVs were the starting point: one built from MQTT/IoT protocol-level traffic features, one from generic network-flow statistics. They were inspected first (row counts, label values, null checks) before any preprocessing decisions were made — the schemas turned out to share a single column in common (the label), which shaped everything downstream.

② Split into non-IID clients

Because the two sources have zero overlapping features, they were treated as two different data domains, each split across its own set of simulated clients, plus an extra Dirichlet(α=0.5) skew on top so even same-domain clients don't see the same class mix. See Section 2 for the real per-client breakdown.

③ Federated training, two strategies

A small MLP is trained across 5 simulated clients using Flower, comparing plain FedAvg against a robust alternative (coordinate-wise trimmed mean), each run once clean and once with 2 of 5 clients poisoning their labels. See Section 3.

④ The same training, over a real network

The identical FL logic is then run again — unmodified — but with the server and clients as separate processes on separate emulated hosts, talking real gRPC over Mininet virtual links through a from-scratch OpenFlow 1.3 controller. See Section 4.

2Dataset Summary

Per-client partitions actually written to data/client_*.csv — row counts, source dataset, and benign/attack balance. This is the real non-IID structure the FL clients trained on.

🏷️ Where the two domains come from

bccc_cleaned.csv — 104 numeric features describing MQTT/IoT protocol behaviour (connection counts, publish timing, packet-length statistics), 18 attack/benign classes, ~2,000 rows each. cic_cleaned.csv — 50 numeric features describing generic network flows (TCP flags, TTL, window size, packet timing), 8 classes, 1,000 rows each. The two share nothing feature-wise, which is exactly why they were kept as separate simulated domains rather than merged.

🧩 Handling the disjoint feature space

To let one global model serve every client despite the schema mismatch, both feature sets were placed into a single 154-column union space: a client from one domain keeps its real values in its own block of columns and gets zeros in the other domain's block. FedAvg then just averages one consistent parameter vector across all 5 clients regardless of which domain they're from.

3FL Results: Clean vs. Poisoned

FedAvg and FedTrimmedAvg (robust aggregation), each run once with no adversarial clients (clean, from results/baseline/) and once with 2 of 5 clients performing label-flipping poisoning (poisoned, from results/). Color = strategy, line style = condition.

🏁 FedAvg

The baseline strategy: every round, the server averages all participating clients' model updates, weighted by how much local data each one trained on. It has no defense built in — a malicious client's corrupted update is blended in with full weight, same as anyone else's.

🛡️ Trimmed Mean

A robust alternative: for every individual model weight, the highest and lowest β fraction of client values are discarded before averaging (β=0.4 here, so with 5 clients, 2 of the 5 values are dropped at each coordinate). The idea is to tolerate a bounded fraction of bad actors without knowing in advance which clients they are.

☠️ Label-flipping poisoning

The simulated attack: a malicious client trains on its real feature data but with 50% of its local labels deliberately flipped (benign ↔ attack) before local training. It still follows the protocol normally — only the content it learns from, and reports back, is corrupted. 2 of 5 clients (40%) do this in every "poisoned" run below.

📐 Why F1/precision/recall, not just accuracy

The test set is heavily attack-skewed (over 90% attack), so a model that always predicts "attack" scores deceptively high on accuracy alone. Recall in particular shows whether the model is still catching real attacks rather than just matching the base rate.

4Networked vs. Non-Networked

The same FedAvg run (2/5 malicious clients) executed two ways: in-process Flower simulation (results/metrics_fedavg.csv) vs. real gRPC traffic over an emulated Mininet network through a custom OpenFlow 1.3 controller (results/networked/).

🖧 Mininet

Mininet emulates a real network — genuine Linux network namespaces, virtual Ethernet links, and a real Open vSwitch bridge — rather than abstractly simulating one. Software running inside it sends actual packets over actual (virtual) wires, which is what lets the exact same client/server code from Section 3 run unmodified here, just talking over a network instead of in-process.

🕹️ Software-Defined Networking

In an SDN, switches don't decide how to forward traffic on their own — they ask an external controller over the OpenFlow protocol. That separation is what would eventually let an IDS-aware controller act on what it sees (e.g. quarantining a flagged host) — a later phase, not built yet.

⚠️ Why the controller isn't Ryu

The plan called for Ryu, the standard tutorial SDN controller. It turned out to be unrunnable on any currently installable Python — unmaintained since ~2021, and even after rebuilding a legacy Python 3.9 environment by hand, its own pinned dependencies (oslo.config, eventlet) no longer work together, and one release's source code turned out to still be Python 2. What's actually running is a from-scratch OpenFlow 1.3 controller — built on the python-openflow protocol library plus plain sockets — implementing the same L2 learning-switch behaviour Ryu's own tutorial controller would have.
